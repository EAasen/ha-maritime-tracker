# v1.2.8 - BarentsWatch Credentials Validation Fix

## Critical Update: TextSelector Validation Error

### Issue Discovered

Users updating to v1.2.7 encountered a NEW validation error on the **BarentsWatch Credentials** screen:

```
Error: "not a valid option at 'barentswatch_client_id'"
Error: "not a valid option at 'barentswatch_client_secret'"
```

This occurs when entering valid API credentials from BarentsWatch.

### Root Cause

Home Assistant 2026.11.0's strict selector validation affects **ALL selector types**, not just SelectSelector and LocationSelector:

- ✅ SelectSelector (dropdowns) - Fixed in v1.2.7
- ✅ LocationSelector (map picker) - Fixed in v1.2.7
- ✅ **TextSelector (text inputs)** - Fixed in v1.2.8 (NEW)
- ❓ NumberSelector (number inputs) - Potentially affected

The credentials schema uses `TextSelector` for both the Client ID and Client Secret fields, which are now getting the same strict validation as other selector types.

### Solution (v1.2.8)

Applied the permissive validator pattern to TextSelector fields in the credentials schema:

**Before (v1.2.7):**
```python
vol.Required(CONF_BARENTSWATCH_CLIENT_ID): selector.TextSelector(...)
vol.Required(CONF_BARENTSWATCH_CLIENT_SECRET): selector.TextSelector(...)
```

**After (v1.2.8):**
```python
vol.Required(CONF_BARENTSWATCH_CLIENT_ID): vol.All(
    selector.TextSelector(...),
    _accept_any_value,  # ← Permissive validator
)
vol.Required(CONF_BARENTSWATCH_CLIENT_SECRET): vol.All(
    selector.TextSelector(...),
    _accept_any_value,  # ← Permissive validator
)
```

### Changes in v1.2.8

| File | Change |
|------|--------|
| `config_flow.py` | Added permissive validator to `_credentials_schema` TextSelector fields |
| `manifest.json` | Version bumped from 1.2.7 → 1.2.8 |

### How This Cascading Issue Happened

1. **v1.2.5**: Fixed LocationSelector error → but broke other selectors
2. **v1.2.6**: Applied broader fix to SelectSelector → but TextSelector still not covered
3. **v1.2.7**: Applied fix to SelectSelector and LocationSelector → TextSelector still broken
4. **v1.2.8**: Extended fix to TextSelector → All selector types now covered

### Why Discover This Now?

The setup flow order matters:
1. Intro (no selectors)
2. **Tracking Mode** (SelectSelector) - v1.2.7 fixed this
3. **Credentials** (TextSelector) - v1.2.8 fixed this
4. Location (LocationSelector) - v1.2.7 fixed this
5. Ports (text input, not selector)
6. Options (SelectSelector) - v1.2.7 fixed this

The user in v1.2.7 got through tracking mode, but then hit credentials screen with TextSelector error.

### HA 2026.11.0 Validation Cascade

Home Assistant 2026.11.0 introduced strict validation that affects ALL selector components:

```
Schema Validation Hierarchy:
├── SelectSelector ✅ (Fixed in v1.2.7)
├── LocationSelector ✅ (Fixed in v1.2.7)
├── TextSelector ✅ (Fixed in v1.2.8)
├── NumberSelector ❓ (May need future fix)
├── BooleanSelector ❓ (May need future fix)
└── Other Selectors ❓ (May need future fix)
```

Each selector type that gets user input validation in the schema layer is affected.

### Technical Note for Developers

The issue demonstrates that **any selector that receives user input** is vulnerable to HA 2026.11.0's strict validation. The pattern to fix is:

```python
vol.All(
    selector.SomeSelector(...),
    _accept_any_value,  # Bypass strict validation
)
```

This is safe because:
1. The selector still renders the proper UI widget
2. The permissive validator passes any value through
3. Handler functions perform actual validation
4. Works with all HA versions (older versions ignore the permissive validator)

### Summary

v1.2.8 extends the v1.2.7 fix to cover TextSelector fields. This should be the final fix needed for HA 2026.11.0 compatibility, assuming no other selector types are introduced in the form flow.
