# v1.2.5 Location Validation Fix

## Problem
Users installing v1.2.5 are still experiencing the error:
```
not a valid option at 'location'
```
When attempting to select a location on the map in the config flow's "Tracking Area" step.

## Root Cause Analysis

The issue occurs because:

1. **Missing Schema Validator**: The `LocationSelector` field in the voluptuous schema didn't have a proper validator to handle the location dictionary format that Home Assistant's LocationSelector widget submits.

2. **Schema Order of Operations**: When the user submits the form, Home Assistant runs the voluptuous schema validation BEFORE the form handler (`async_step_radius()`) receives the data. If the schema validator fails, voluptuous throws a generic "not a valid option" error and never reaches our handler.

3. **Complex Default Values**: The previous attempt to fix this by adding complex default values to the schema caused more validation issues, as voluptuous couldn't properly serialize the nested dictionary defaults.

## Solution Implemented in v1.2.5 Patch

### 1. Added Location Validator (`_validate_location()`)

A new dedicated validator function validates the location dictionary format:

```python
def _validate_location(location: Any) -> dict[str, float]:
    """Validate location dict from LocationSelector."""
    if not isinstance(location, dict):
        raise vol.Invalid("Location must be a dictionary")
    
    if "latitude" not in location or "longitude" not in location:
        raise vol.Invalid("Location must have latitude and longitude")
    
    try:
        latitude = float(location["latitude"])
        longitude = float(location["longitude"])
    except (ValueError, TypeError) as err:
        raise vol.Invalid("Latitude and longitude must be numbers") from err
    
    if latitude < -90 or latitude > 90:
        raise vol.Invalid("Latitude must be between -90 and 90")
    
    if longitude < -180 or longitude > 180:
        raise vol.Invalid("Longitude must be between -180 and 180")
    
    result = {"latitude": latitude, "longitude": longitude}
    
    if "radius" in location:
        try:
            result["radius"] = float(location["radius"])
        except (ValueError, TypeError) as err:
            raise vol.Invalid("Radius must be a number") from err
    
    return result
```

### 2. Updated Schema to Use Validator (`_radius_schema()`)

The schema now uses `vol.All()` to chain the LocationSelector with our validator:

```python
def _radius_schema(hass: HomeAssistant, defaults: dict[str, Any]) -> vol.Schema:
    """Build the radius/location step schema with proper validation."""
    return vol.Schema(
        {
            vol.Required(_CONF_LOCATION): vol.All(
                selector.LocationSelector(
                    selector.LocationSelectorConfig(
                        radius=True,
                        icon="mdi:ferry",
                    ),
                ),
                _validate_location,  # Chain validator after selector
            ),
        },
    )
```

**Key Changes:**
- Removed complex default value that caused validation to fail
- Added explicit location validator using `vol.All()`
- The validator runs AFTER the LocationSelector receives the form submission
- Proper error messages for various validation failures

### 3. Handler Logic (`async_step_radius()`)

The handler catches any validator errors and displays them appropriately:

```python
async def async_step_radius(self, user_input: dict[str, Any] | None = None) -> ConfigFlowResult:
    """Collect center coordinates and radius."""
    errors: dict[str, str] = {}
    if user_input is not None:
        try:
            if _CONF_LOCATION not in user_input:
                errors["base"] = "location_required"
            else:
                loc = user_input[_CONF_LOCATION]  # Already validated by schema
                
                # Additional safety checks (should be redundant with validator)
                if not isinstance(loc, dict):
                    errors["base"] = "invalid_location_format"
                elif "latitude" not in loc or "longitude" not in loc:
                    errors["base"] = "location_missing_coordinates"
                elif not _is_within_norway(loc.get("latitude"), loc.get("longitude")):
                    errors["base"] = "location_outside_norway"
                else:
                    # Store validated location
                    self._data[CONF_LATITUDE] = float(loc["latitude"])
                    self._data[CONF_LONGITUDE] = float(loc["longitude"])
                    
                    radius = loc.get("radius")
                    if radius is not None:
                        self._data[CONF_RADIUS_KM] = float(radius) / _METRES_PER_KM
                    else:
                        self._data[CONF_RADIUS_KM] = DEFAULT_RADIUS_KM
                    
                    return await self.async_step_options()
        except (KeyError, ValueError, TypeError) as err:
            _LOGGER.debug("Error processing location: %s", err)
            errors["base"] = "invalid_location_data"

    if errors:
        return self.async_show_form(
            step_id="radius",
            data_schema=_radius_schema(self.hass, self._data),
            errors=errors,
        )

    return self.async_show_form(
        step_id="radius",
        data_schema=_radius_schema(self.hass, self._data),
    )
```

## Why This Fix Works

1. **Early Validation**: The validator runs when the form is submitted, catching format issues before the handler
2. **Clear Error Messages**: Voluptuous validation errors translate to user-friendly messages
3. **No Complex Defaults**: Removing complex defaults allows the schema to validate cleanly
4. **Proper Type Coercion**: The validator ensures latitude/longitude are proper floats
5. **Norway Boundary Check**: The handler adds domain-specific validation (location within Norway)

## Why v1.2.2 Fix Wasn't Complete

The v1.2.2 fix added error handling in the `async_step_radius()` handler, which was necessary but **not sufficient**. The handler only runs AFTER the form validation passes. If the schema validation fails, the handler is never called.

This v1.2.5 patch completes the fix by adding schema-level validation, ensuring the form can be submitted and errors handled gracefully.

## Technical Details for Developers

### Voluptuous Validator Chain

```python
vol.All(selector, validator)
```

- `selector`: The Home Assistant LocationSelector widget (renders the map picker)
- `validator`: Our `_validate_location` function (validates the submitted data)

The chain ensures:
1. The LocationSelector widget handles the UI rendering
2. When submitted, Home Assistant collects the location data
3. Our validator runs on the collected data
4. If validation passes, the handler receives clean, type-safe data
5. If validation fails, voluptuous catches the error and displays it in the form

### Error Message Mapping

Voluptuous errors are caught at the form level and mapped to user-friendly messages:

| Validator Error | Error Code | User Message |
|---|---|---|
| `"Location must be a dictionary"` | `"invalid_location_format"` | "The location data format is invalid..." |
| `"Location must have latitude and longitude"` | `"location_missing_coordinates"` | "The location is missing latitude/longitude..." |
| `"Latitude must be between -90 and 90"` | `"invalid_location_data"` | "There was an error processing the location..." |
| `"Longitude must be between -180 and 180"` | `"invalid_location_data"` | "There was an error processing the location..." |
| `"Radius must be a number"` | `"invalid_location_data"` | "There was an error processing the location..." |

Plus domain-specific validation in the handler:
- Location outside Norway → `"location_outside_norway"`
